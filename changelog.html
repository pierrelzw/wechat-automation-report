3.14.22026-07-23

修复 🐛

  • 粘贴微信号后的等待从 0.3 秒提到 0.8 秒（微信拉群 + 全部转发）——为什么这么改：0.3 秒下粘贴结果未必渲染完，下一个按键会打在旧画面上，用于判定的截图反映的是粘贴之前的状态，于是一个有效联系人被误判成 [suspect]，运营还得人工核对、整批重跑。这条分支正是 3.14.0 的「按弹窗已选计数判定」没覆盖到的那条——计数判定只在企业微信生效，微信拉群和微信转发仍然靠帧差判定，仍然依赖粘贴已经渲染完成。0.8 不是拍脑袋：定 inviteSearchSettleSec 的那次 spike 已经测出 0.3 过低、0.9 足够，0.8 落在其内。企业微信拉群走另一条分支，本次不动。
    • 代价：每个收件人多等约 0.5 秒，227 人的一轮约 +2 分钟。相比一次误判导致的人工核对加重跑，这个代价可以接受。固定延时是钝器，长期正解是「轮询到画面稳定」（issue #165）。

测试 🧪

  • 端到端断言改为按收件人身份绑定，不再按行号——为什么这么改：原先 assert_status 3 "success" 是按行号定位的，CSV 一重排断言就会落到另一个联系人身上、却依然通过；断言还在，保护没了。现在按 wechat_id / recipient 查行。
  • 补上从未被验证的 [suspect] 子类——原断言的标签写着「message=[suspect] …」，但代码只比对 status 列，从来没看过 message。failed 本身分不出「坏收件人」和「别的失败」，而运营看的正是子类。
  • 加一条 SESSION_END 完整分解断言，并把「截图数 ≥6」「检测器 ≥3 个联系人」这类下限改成精确值——固定 fixture 下这些数是确定的，用下限等于放过「少跑了一个人」这种回归。
  • 端到端跑得更快：拉群测试的四行并进同一个群（少一次弹窗会话），发送测试去掉冗余的第二次成功发送（一条正常发送 + 一条坏收件人检测，两条路都还在）。
3.14.12026-07-23

修复 🐛

  • 同一批里重复出现的收件人会互相抵消，两行都被记成成功（issue #234）——为什么这么改：多选弹窗里第二次粘贴同一个 id 再回车，落点是已经勾选的那一行，回车把第一次的选中 toggle 掉了。结果这个人一条都没收到，而两行 CSV 都写着 success。bugs/20260720_161930 那批就是这样：155**1263 在同一批出现两次（p5 和 p7），实际零送达。现在分批之后、进弹窗之前先做批内去重：保留首行，后续重复行不进弹窗。跨批重复不动——那是两次独立的弹窗会话，属合法的重复发送。send 明确排除：它按 (inviter, recipient) 分批，同一收件人的多行就是**多消息 seq 设计，去重会直接丢消息。
    • 与 3.14.0 的「按弹窗已选计数判定」是互补而非重复：那个负责在选中出问题时发现，这个负责让重复项根本不进弹窗。
    • 被跳过的行镜像首行的真实结果：首行成功 → success + [skip] 同批重复收件人（已随首行发送）；首行失败 → 同样失败 + [blocked] 同批首行未送达，请重试（可被 --retry-failed 捞回）；该批次没跑 → 保持 pending 下次重放。记 success 而不是 failed，是因为这个人确实收到了（随首行发出），记失败会让运营去重发一条已经发过的消息。
    • 一个可见后果：[skip] 行在会话汇总里落「跳过」桶、不落「成功」桶（analyze_session_state 先看 message 前缀再看 status）。所以「成功 N」是真正发出去的条数，重复行单独计。这是既有 [skip] 语义的直接结果，不是新行为。
3.14.02026-07-22

新增 ✨

  • 逐人选人改用 picker「已选择 N 个」计数器做绝对判定（issue #232 / #235）——为什么这么改：原来的判据是差分哈希（对弹窗连拍三到四帧比 MD5），它只回答「画面变了吗」，不回答「往哪变」。于是三种截然不同的结果在哈希上完全同构、全判 success：正常选中一个人、什么都没选上、以及把上一个人取消掉。第三种最坏——它让收件人数不升反降，却被记成成功。生产 run（bugs/20260720_161930，企微转发 233 行 / 26 批）因此把 16 个从未进入收件人列表的人写成 success，日志报 227 成功、实际只选中 211。计数器把这三种拆开了：+1 成功、不变 = 没选上、变少 = 取消了上一位（本人和上一位一起标 suspect）。新增 wca-ax --selected-count 子命令读这个数字，新增引擎 handler findPickerSelectedCount / 判定 handler evalSelectedCountVerdict。
  • 判定策略可配置、且天然可回滚：apps.<bundleId>.<workflow>.verify_strategies 现在是 ["ocr_selected_count", "hash_2point"]——先绝对、后差分。OCR 读不到计数器时不返回判定，而是落到原来的哈希路径，行为与 3.13.0 完全一致。这条回退是刻意的，而且真机证明它是必需的：企微转发与邀请的计数器都已取证可读，但 picker 在已选 0 人时根本不渲染这行字——所以「第一个人就没选上」必然读不到计数，只能靠 hash 兜底。两种判据互补：计数器独有「变少」这一维，hash 独有「已在群内 vs 没搜到」的区分，因此 hash 不能删。微信（非企微）转发 picker 没有这个计数器，该路径上本方案惰性、行为不变。回滚方式是从该列表里删掉 ocr_selected_count，改配置即可，不用改代码。
  • 新增配置块 picker_selected_count（top_fraction=0.15、min_confidence=0.1）。top_fraction 是弹窗高度的比例而非像素偏移，因此与分辨率无关（计数器固定在距顶部约 6–8% 处，实测有效区间 0.08–0.40，默认值两端各有近一倍余量），不需要按机器指纹分桶。

修复 🐛

  • 转发点「分别发送」前新增一道独立核对闸门（issue #233）——为什么这么改：批次末那行 分别发送成功（弹窗已关闭），成功收件人=N 看着像一次验证，其实 N 就是同一批 per-task 判定的累加，它和逐人判定永远自洽，逐人错多少它就跟着错多少。#231 里 b25 报 8、实际 6，这行日志毫无察觉；「弹窗已关闭」也只证明按钮点击被接受了，不证明每个人都收到了。现在点发送之前独立读一次计数器，与本批唯一收件人数比对（wca/batching.py 不去重，一批里合法地可能有重复行——#231 的 b26 就是 8 行 / 7 唯一）。比对的是一个区间而不是单个数：下限＝本批判定为成功的唯一收件人数（这些人必须在弹窗里，少一个就说明有人被记成已送却根本不在），上限＝本批实际输入过的唯一收件人数（弹窗不可能比这更多），中间那段差额就是 suspect——本来就没把握的人，在不在都不算异常。落到区间外才不发送，整批标 failed 并写明「应选中 N 人、实际选中 M 人」。之所以不要求严格相等：一批 9 人里只要有 1 个 id 没选中，严格相等会把整批拦下、另外 8 个已正确选中的人一个都收不到——那是把「静默少发」换成了「响亮地全不发」。读不到计数器时放行（fail-soft）——读不到不等于漏选，不能因为 OCR 失效就拦下正常批次。成本约 0.33 秒/批，26 批的 run 里合计约 9 秒。
  • 那行误导的 成功收件人= 日志已按「supersede by deletion」删除，改为打印闸门实际读到的人数；闸门没读到时如实写「本批已选人数未能核对」，而不是拿一个从没被核对过的数字顶上。

  • 三个新测试均已并入 make ci，不需要微信、不需要辅助功能权限。
3.13.02026-07-20

新增 ✨

  • 企业微信：开启「群聊邀请确认」的群，邀请多一步「发送」确认（issue #227）——为什么这么改：之前的流程假设点完「邀请」就发出去了。但群主开启「群聊邀请确认」后，企微会再弹一个独立对话框（标题「提示」，正文「群主或群管理员已启用"群聊邀请确认"」，一个选填的理由输入框，按钮「取消 / 发送」），必须点「发送」邀请才会转给群主/管理员审批。旧代码不认识它，被后置成功门当成「弹窗没关掉 = 邀请失败」，于是按 ESC 把它关掉——等于主动取消了这次邀请，还报了句误导的「可能已被对方删除」。现在点完「邀请」后追加一次条件式定位：找到「发送」就点，找不到（未开启该设置的群）就什么都不做，两种群共用一条代码路径，不判断也不配置邀请人是不是管理员。真机验证 企微自动拉群测试 success、企微批量群邀请test（未开启该设置）不触发第三步且无回归。
  • 新增配置项 apps.<bundleId>.invite.send_confirm_labels（默认 ["发送","Send"]），仅为该按钮文案，便于客户端改字或英文版时免重新打包。
  • 会话日志第一行记录版本号（[INFO] wechat_automation v3.13.0 workflow=invite dry_run=false）——为什么这么改：issue #226 的定位依赖"这次跑的是 3.12.5"，而这个信息日志里根本没有，是靠操作同学回忆出来的。现在它是 run() 里最先写的一行，早于任何可能中止的步骤（配置校验、辅助功能权限预检），因为预检失败正是最需要知道版本的时候。单独一行而不是挂在 SESSION_START 上，就是为了这个顺序；VERSION 读不到时记 unknown，绝不因此中断会话。

修复 🐛

  • apps.<bundleId>.invite 的三个文案配置项恢复生效（本分支自身引入的回归）——为什么这么改：删除 picker_confirm_labels / picker_cancel_labels 时，连带把旁边 picker_titles、delayed_confirm_labels 以及本次新增的 send_confirm_labels 的赋值行一起删掉了。三者仍被解析、仍存进临时变量，但再也没有写回 appProfile* 属性——改了配置等于没改，永远只用编译期默认值。因为出厂配置的值恰好等于默认值，行为上看不出来。这直接推翻了 send_confirm_labels 的存在理由（"客户端改了文案时不用在没有开发环境的目标机上重新打包"）。已补回三行赋值，并把 init 日志里的计数改为实际文案，这样配置没生效可以一眼看出来（计数改不改都是 2）。
  • invite_ocr.enabled=false 不再是这两个条件式弹窗的回滚开关——延迟「邀请」和「确认发送」只能靠 OCR 定位（弹窗是临时的，plist 里没有记录锚点），关掉 OCR 只会让每一步空转到超时再报「识别不出按钮」。现在检测到 enabled=false 时立即返回并在日志点名这个配置项，而不是烧掉 5 秒预算让人以为是 OCR 认错了。AGENTS.md 对应旋钮说明同步修正（该开关只回滚有 plist 兜底的按钮）。
  • 邀请确认改为「所有弹窗清空」判定，识别不出按钮一律报错——为什么这么改：原来的成功判据是 checkInvitePickerOpened，它只看「添加群成员」这一个弹窗，而「确认发送」是独立顶层窗口，它根本看不见——之前没出事只是因为提示弹窗出现时添加群成员恰好还叠在后面，属于运气不是设计。现在每一步都问同一个问题：弹窗是不是全没了（窗口数≤1 且无 sheet，与每批干净基线同一定义），全没了才算成功。流程也从「固定超时」改为「看屏幕状态」：点完确定 → 弹窗没了就结束（无需二次确认的群）→ 否则找「邀请」点击 → 弹窗没了就结束（管理员群）→ 否则找「发送」点击 → 弹窗没了才算成功。副作用是无需二次确认的群不再空等 5 秒，第一次窗口读取（约 100ms）就返回。
  • 「多次识别不出按钮」现在是一个会报出来的失败，不再被当成「本来就没有」——这是 issue #226 静默假成功的根源：超时被翻译成「小群，无需二次确认」这个语义结论，而超时真正的含义只是「我没看见」。现在只要弹窗还在却识别不到已知按钮，就 failed 并在日志写明尝试了哪些文案、试了几次、扫了哪块区域（每次尝试的 OCR 候选列表也在上方），同时存一张截图。无论企微将来加出第几个弹窗，判据都不用改。
  • 批次异常时，选人阶段记下的 success 会被回收——选中 ≠ 已邀请：每个收件人在选人阶段就带着 success 进了结果集，但「确定→邀请→发送」还没点。正常路径早有降级逻辑（inviteFailed 时改回 failed），异常路径没有，于是确认阶段一抛错就绕过它，真机实测出现过「批次报错 status=error，任务却写 success」。现在异常处理里补上同样的回收，且失败文案按实际观察到的状态区分，不再一律「可能已被对方删除」。
  • 新增 make lint 静态检查 scripts/check-handler-calls.sh——AppleScript 的 handler 调用是运行时解析的，所以改名漏改调用点能正常编译，只在那条分支真正执行时才炸 -1708。而那条分支可能恰好是 e2e 够不到的：invite e2e 跑在 WCA_SUPPRESS_INVITE_FINAL_CLICK=1 下，停在「邀请」点击之前，所以下游「确认发送」里的坏调用一路绿灯发了出去。新检查逐个校验 workflow 里的 engineRef's <handler> 是否在引擎中存在，不需要微信、不需要辅助功能权限、可进 CI，覆盖所有调用点而不管 e2e 能跑到哪几条。
  • 点击抖动过大导致小按钮被点空（全局默认 sigma 5.0→2.0、max_radius 12→5）——为什么这么改：click_jitter 是防指纹用的随机偏移，但 max_radius 实际是逐轴夹紧，即 ±N 的方框而非半径，对角线最大位移达 N×√2 ≈ 17pt。而「发送」按钮只有约 24pt 高（半高 12pt），抖动半径和它半高相当，等于抛硬币：真机实测 target=(1194,575) actual=(1191.0,584.7) 点在按钮边缘外，弹窗没关，随后被后置门 ESC 掉。之前一直没暴露，是因为其它按钮（如「确定」约 44pt 高）足够大扛得住。抖动的意义是模拟人手，而人手不会点到按钮外面去，所以按最小可点目标重新定尺寸而非给单个按钮开特例。改后实测偏移收敛到 (-1.4,-4.7)，稳定落在按钮内；防指纹的随机性保留。
